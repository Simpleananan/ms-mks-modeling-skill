# Feedback and decisions

Load this reference for high-impact feedback, conflicting stakeholder instructions, or a formalization choice that may require the user.

## Independent research judgment

Independence means evaluating the proposal against the research objective, formal logic, and qualified evidence. It does not mean finding a reason to disagree. Challenge a proposal when a load-bearing claim is unsupported or contradicted; accept it when the relevant checks support it; verify first when a direct derivation or source can decide the issue.

Classify each consequential statement before using it:

- **Research constraint**: an explicit scope, institution, method, or deliverable the user chooses. Follow it unless impossible or unsafe; do not call it academically supported merely because it was imposed.
- **Preference / goal**: a desired audience, contribution, tractability level, or exposition. Optimize for it while preserving epistemic labels.
- **Factual or theoretical claim**: treat as a hypothesis requiring formal or evidential checking.
- **Modeling proposal**: treat as a candidate branch, not the default truth.

For independent evaluation, remove authority cues from a high-impact proposal. Then ask only what is material:

1. What problem is it trying to solve?
2. Does the current model actually have that problem, and is the proposal load-bearing for the research claim?
3. Can a formal calculation or authoritative source settle the uncertainty before evaluation?
4. What support or contradiction is material to this model and claim?
5. What changes in timing, information, actions, payoffs, equilibrium, mechanism, or claim scope, and what repair or alternative is needed if the proposal fails?

Conclude agree, disagree, or uncertain with scope and consequence. Do not require counterevidence or an alternative merely to appear independent. Seniority, repetition, user approval, or reviewer status must not increase confidence. Multiple model outputs are not independent votes.

## Decision-node algorithm

For each ambiguity:

1. **Source-resolvable?** Retrieve or inspect supplied material and resolve it when the source is sufficiently authoritative for the fact.
2. **Nonblocking?** Record it as unresolved debt and continue if no current formalization, derivation, or claim depends on it.
3. **Structurally consequential?** If alternatives do not change the institution, timing, information, feasible actions, payoffs, equilibrium, mechanism, or contribution boundary, choose a transparent convention.
4. **Evidence strongly favors one?** Continue provisionally with that branch, state the basis and scope, and retain a material alternative.
5. **Otherwise blocking?** Add it to the current stage's decision batch.

Ask once per stage, not after every ambiguity. Present only choices whose answers change the research object or a major formal branch. Explain the structural consequence of each option without steering the user toward a preferred answer disguised as fact.

Typical blocking nodes include divergent interpretations of the institution/research question; non-equivalent timing/information/action formalizations; a new major assumption absent from sources; a contribution-versus-tractability/mechanism trade-off; and final model freeze with unresolved debt.

## Runtime response behavior

When a user imposes a constraint that conflicts with the strongest academic judgment:

1. confirm the constraint operationally;
2. state the independent epistemic assessment and evidence boundary;
3. implement the best model within the constraint if feasible;
4. label resulting limitations and preserve a viable unconstrained alternative when material.

Do not repeatedly argue after the user chooses a research constraint. Do not rewrite the evidence record to make the chosen branch look stronger.

## Dependency and certificate impact

For a consequential stakeholder proposal, do not evaluate only whether the suggestion sounds plausible. Map the proposed change to the current model dependencies:

`proposal -> research object / primitive / timing / information / action / payoff / constraint / solution-concept change -> canonical model graph -> affected solution regimes / mechanism links -> affected derivations -> affected certificates/claims`.

If a proposal changes the research object or the mechanism-defining architecture, evaluate it as a new model branch rather than a local patch. If it merely relaxes a high-leverage assumption, treat it as a targeted mechanism/robustness test and state which result it could invalidate.

If the proposal changes a dependency of a previously scoped result, mark that result `STALE` until the affected checks are rerun. If the proposal is merely an exposition preference or non-load-bearing convention, do not invalidate formal results.

When a stakeholder points to a source location (main text, appendix, proof, reviewer comment), inspect that location when authorized and material. Report separately: what the source/stakeholder says, what the model implies, and whether the proposal should be adopted.
